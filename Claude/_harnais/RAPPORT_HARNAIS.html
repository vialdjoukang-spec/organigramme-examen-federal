Le gaspillage ne vient pas de ce que les agents écrivent : il vient de ce qu’ils relisent à chaque tour. Le harnais coupe ces relectures par des scripts gratuits et une mémoire persistante, et il mesure automatiquement l’économie réelle dès la reprise.

Fuites identifiées, par ordre d’impact

  1. Le nombre de tours pèse au carré. Chaque tour relit tout le contexte, qui grossit d’environ 1.3 k tokens par tour : le coût de relecture vaut T·C0 + g·T²/2. Un agent à 2 DX fait 256 tours et finit à 433 k tokens.
  2. Un socle de 80 k tokens relu à chaque tour par chaque agent : outils, instructions, et le CLAUDE.md du dépôt MEDINA (28 Ko), sans rapport avec ces cours.
  3. Relectures évitables : AIPS entières (40–120 Ko), extraits du prompt L1 (142 Ko), cours entiers, sources déjà lues par un autre agent.
  4. Fautes mécaniques laissées à l’audit : les rubriques grossesse et allaitement adoucies et les dates d’AIPS fausses se détectent par script. Sur le LOT_024, aips_fiche.py a retrouvé sans modèle les défauts critiques et graves que l’audit avait relevés (14 défauts bloquants).
  5. Boucle principale trop chargée : contexte jusqu’à 900 k tokens ; chaque notification relit tout.
  6. Agents perdus : 41 M dépensés par des agents arrêtés sans rendre leur travail.

Modèle mathématique multivarié

1. Identité mécanique (vérifiée agent par agent, R² = 0.9995) : coût = 0,1 · Σtours contexte + 1,25 · cache écrit + 5 · sortie, avec Σ contexte ≈ T·C0 + g·T²/2.

2. Régression a priori : log(coût) selon le type de tâche ; R² = 0.43, écart-type résiduel 0.67 en log ; intervalles par bootstrap (2 000 tirages).

3. Monte-Carlo d’un LOT standard (Phase A, porte P1, 5 agents × 2 DX, 4 audits, 2 corrections, 2 contre-audits, 2 recherches ; 20 000 tirages), avec un effet LOT calibré (difficulté commune : ×1.18 en moyenne, écart-type log 0.12).

Flux d’un agent : brief de 2 Ko → carnet + MEMOIRE.md + index des sources → rédaction en un fichier de contenu → portes gratuites (controle3, verif_aips, aips_fiche, abréviations) → note au carnet → commit → la veille met à jour mémoire, progression et modèle.

Mémoire persistante : trois couches

  1. MEMOIRE.md par LOT (résumeur) : sur le LOT_023, 12 Ko au lieu de 950 Ko de cours, audits et sources.
  2. Carnet de chaque agent (memoire_agent.py) : une ligne par fait établi ; un agent qui reprend ou remplace un autre ne relit rien.
  3. Caches partagés : sources (texte brut hors dépôt, index dans le dépôt) et AIPS (rubriques compactes).

Suivi de son fonctionnement : suivi.py compte, par agent, les appels à la mémoire et les accès web ; la page de progression les affiche. Un agent qui refetch une source déjà en cache est une fuite visible.
